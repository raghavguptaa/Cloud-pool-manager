# Data provenance

Everything in this directory is **real telemetry captured from a live AWS deployment I ran in
March 2026**. The account has since been closed, so none of it can be re-exported. That makes
these four files the only irreplaceable artifacts in the repository — they are committed verbatim
and treated as read-only inputs.

Nothing here is synthetic, resampled, smoothed, or back-filled. Where the captured data disagrees
with the original write-up, the disagreement is recorded below rather than edited away.

### `baseline_events.csv` / `governor_events.csv`

Transcribed from the spreadsheets kept during the runs. Original cells stored Excel time serials;

## Timestamp reconciliation

Two clock-labelling defects exist in the original material. Both are resolved; neither required
changing a single measured value.

### 1. The governor state timeline is labelled UTC+06:00, not IST (UTC+05:30)

`governor_events.csv` rows carry an IST clock time that is **30 minutes ahead of true IST**. The
CPU values prove it — under `UTC+06:00` all three overlapping rows match the export exactly, and
under true IST none of them land inside the captured window at all:

| Recorded label | as UTC+05:30 | as UTC+06:00 | CPU in `governor_1min.csv` | Timeline says |
|---|---|---|---|---|
| 05:43 PM | `12:13Z` — no data | `11:43Z` | `29.9078…` | 29.90 ✅ |
| 05:44 PM | `12:14Z` — no data | `11:44Z` | `50.1232…` | 50.10 ✅ |
| 05:45 PM | `12:15Z` — no data | `11:45Z` | `49.9533…` | 49.90 ✅ |

A three-for-three match on independently recorded CPU values is not a coincidence: the IST column
was computed with a `+06:00` offset instead of `+05:30`. `governor_events.csv` therefore keeps the
original label in `time_ist_recorded` and adds `time_utc_start` / `time_utc_end`, recovered as
`recorded − 06:00`. Those UTC columns are what the replay joins on.

The baseline timeline is unaffected — its UTC and IST columns are a correct `+05:30` pair and line
up with `baseline_5min.csv` to the second.

### 2. The original figure axes are mislabelled

- **Original Fig. 1** plots `18:55 / 19:00 / 19:05` on an axis titled *Time (IST)*. Those are the
  UTC timestamps from the export; true IST would be `00:25 / 00:30 / 00:35` the following day.
- **Original Fig. 2** plots the `+06:00` clock described above, also titled *Time (IST)*.

Figures regenerated by `sim/replay.py` are plotted and labelled in **UTC**, matching the export,
with IST shown only as a secondary annotation.

## Known open question — the tail of the governor run

This one is *not* resolved, and is deliberately left visible.

The retained export stops at `11:47:00Z`. The recorded scale-in event is `11:48:00Z`, so **the
export ends one minute before the scale-in it is supposed to evidence.** Worse, inside the window
the two sources disagree:

| UTC | `governor_1min.csv` | Original Fig. 2 at the same clock position |
|---|---|---|
| `11:45Z` | 49.95 % | ≈ 50 % ✅ |
| `11:46Z` | **49.95 %** | **≈ 15 %** ❌ |
| `11:47Z` | **29.39 %** | **≈ 1.5 %** ❌ |
| `11:48Z` | *no data* | ≈ 0.3 % |

The rising edge agrees perfectly; the falling edge does not. The most likely explanation is that
the original figure was drawn from a longer export — one that ran several minutes past `11:47Z` —
and that the CSV retained here is a truncated re-pull of the same metric. That cannot be confirmed:
the account is gone and the longer export was not kept.

**Consequence, stated plainly:** the *scale-in* half of the governor run is supported by the
hand-recorded timeline and the original figure, but **not** by the retained CSV. The spike-detection
and mitigation half is fully supported by all three. `sim/replay.py` plots and asserts against the
CSV only — the primary artifact — so the regenerated figure's tail legitimately differs from the
original figure's tail. See *Limitations* in the README.

## Reproducing the capture

Not possible from this repository — the account is closed. The `terraform/` module does stand the
same architecture up in a fresh account, and `var.scaling_mode` selects either arm, so an
equivalent capture can be run again; it would be new data, not this data.
